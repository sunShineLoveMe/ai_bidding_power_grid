## 一、评审依据与方法

本评审基于两个事实源对照得出，不是凭印象：

1. **客户参考稿真实解析（基准）**
   - `assets/template_words/技术文件 - 10kV架空绝缘导线-新疆.docx`：33 个 section、1291 个非空段落、82 张表、420 张内嵌图，约 500 页级。
   - `assets/template_words/商务文件 - 10kV架空绝缘导线-新疆(1).docx`：12 个 section、46 条目录、约 170 页级。
   - 解析方式：`python-docx` 读取页面设置、页眉页脚、段落样式、字号、字体、页码字段、目录层级。

2. **本项目导出代码静态逻辑**
   - `backend/export/md_to_word.py`：
     - 模板 profile：`DOCX_TEMPLATE_PROFILES`（`formal_bid_standard` / `technical_bid_standard` / `business_bid_standard`）
     - 版式落地：`set_document_format`、`_add_cover_page`、`_add_toc_page`、`process_table`
     - 新疆参考分支判定：`_is_xinjiang_reference_profile`、`_heading_run_spec_for_profile`
   - 三段导出链路：`build_project_bid_markdown` → `convert_md_to_word` → `refresh_docx_fields_with_soffice`

### 方法局限（重要）

本评审是「客户稿实测参数 + 导出代码静态逻辑」对照，**未起服务跑一份真实 DOCX 并逐页渲染比对**。涉及渲染观感（封面留白、分页、字体替换实际效果）的条目，均已标注「需真实导出复核」。建议在专家评审通过任一整改项后，用真实导出链路出片复核，把结论从「代码推断」升级为「渲染实测」。

## 三、已经对齐的部分（做得对，不要回退）

代码中 `_is_xinjiang_reference_profile` 分支已基本踩准客户风格，以下项已对齐：

1. **页边距与页眉页脚距**：`2.54 / 3.17`、页眉距 `1.5`、页脚距 `1.75`，与客户稿完全一致。
2. **目录**：4 级、宋体、点引导线、`PAGEREF` 页码字段，LibreOffice 字段刷新。
3. **标题样式**：统一宋体 12pt 加粗、左对齐（`_heading_run_spec_for_profile` 返回 `("宋体", 12, True)`），符合客户「标题不放大、不居中」的实际做法。
4. **封面文件类别区分**：大标题统一「投标文件」，另起一行「文件类别：技术 / 商务」，与客户封面写法一致。
5. **签章口径**：投标人行「（盖单位章）」、签章行「（签字）」与客户一致。

## 四、主要偏差与整改建议

> 优先级：P0 = 肉眼最易发现的不一致 / 影响交付观感；P1 = 进一步贴近客户稿；内容层 = 交付边界问题需与客户确认。

### 偏差 1：页眉多了文字，客户是空白页眉【P0】

- **现状**：`set_document_format` 无条件写入页眉 `header_left \t header_file_type`（左侧项目名、右侧文件类型）。
- **客户稿**：技术标、商务标全部 section 页眉**均为空白**。
- **根因**：`formal_bid_standard` 通用规则与新疆参考稿冲突，xinjiang profile 未对页眉做差异化处理。
- **建议**：命中 xinjiang reference profile 时页眉留空。
- **需真实导出复核**：是。

### 偏差 2：页脚页码格式不符【P0】

- **现状**：页脚强制「第 X 页 共 Y 页」（`PAGE` + `NUMPAGES` 两个字段）。
- **客户稿**：页脚为**居中纯数字**单字段页码（`PAGE \* MERGEFORMAT`，`decimal`），无「第…页 / 共…页」。
- **建议**：xinjiang profile 下页脚只放居中 `PAGE` 字段，去掉 `NUMPAGES` 和「第/共」文字。
- **需真实导出复核**：是。

### 偏差 3：首页 / 封面页码策略不符【P0 / 中】

- **现状**：`different_first_page_header_footer = True` 且清空首页页眉，封面无页码。
- **客户稿**：`different_first_page = False`，封面纳入连续 `decimal` 页码（目录页码从 3 起）。
- **影响**：项目导出的目录页码基准与客户稿不一致。
- **建议**：xinjiang profile 下关闭首页特殊化，统一连续页码。
- **需真实导出复核**：是（需确认封面是否要显示页码，或仅纳入计数）。

### 偏差 4：封面字号偏小【P1】

- **现状**：投标人 / 签字 / 日期均压到 12pt，招标编号混入 14pt 的 formal_fields。
- **客户稿**：招标编号单独一行 18pt 加粗紧跟项目名；投标人 16pt、签字 15pt、日期 16pt。
- **影响**：封面视觉重量比客户稿轻。
- **建议**：按客户字号校准封面各行。
- **需真实导出复核**：是。

### 偏差 5：正文东亚字体存在字体替换风险【P0 / 稳定性】

- **现状**：xinjiang profile 正文东亚字体仍是 `FangSong_GB2312`，1.5 倍行距、首行缩进 2 字符。
- **客户稿**：全篇宋体（SimSun），正文 / 应答多为 10.5pt 非缩进叙述体。
- **风险**：阿里云线上容器若缺 `FangSong_GB2312` 字体，PDF / 预览会发生字体替换；客户稿用宋体反而更稳。
- **建议**：xinjiang profile 正文东亚字体改宋体，规避字体缺失风险（10.5pt 是否采用需结合生成正文性质判断，见下条说明）。
- **补充说明**：项目正文是 AI 生成的正式叙述正文，客户大量是粘贴的招标技术规范原文，两者性质不同，不必强行统一为 10.5pt 非缩进；但字体应优先宋体。
- **需真实导出复核**：是（建议在缺字体的环境模拟验证）。

### 偏差 6：无法稳定产出「（一）（二）」国网混合编号【P1 / 结构性，最影响"像不像"】

- **现状**：编号依赖模型生成的 Markdown 标题 + `_renumber_body_markdown_headings`，难以稳定还原客户的混合编号体系。
- **客户稿**：一级 `（一）` → 二级 `1.` → 三级 `1.1` → 四级 `1.1.1` → 五级 `1）`。
- **影响**：这是导出物「看起来不像中标稿」最核心的结构差异。
- **建议**：把 `reference_outline` 从纯文本清单升级为真正的编号模板规则（按层级套用对应编号格式）。
- **需真实导出复核**：是。

## 五、体量 / 完整度差距（内容层，需与客户确认交付边界）

- **客户技术标**：420 图 / 82 表 / 500 页级，主体为「参数特性表（逐规格）+ 技术规范点对点应答 + 检验报告整页 + 原材料组部件供应商证明」。
- **本项目导出**：当前存在两层图片上限：`DOCX_TOTAL_ASSET_IMAGE_LIMIT` 控制 `build_project_bid_markdown` 从知识库自动选图的总量，`DOCX_MAX_IMAGES` / `MARKDOWN_IMAGE_MAX_COUNT` 控制 Markdown 转 Word 时实际插入图片的总量，默认均为 24 张；整体形态更接近「正文 + 少量配图」。
- **定性**：这不是排版 bug，而是交付内容组织方式与真实中标稿的量级差距。技术参数特性表逐规格、点对点应答、检验报告整页扫描等正式投标主体内容，目前未按客户量级组织。
- **建议**：与客户确认 MVP 交付边界，避免演示时被认为「内容太薄」。此项需要产品 / 业务侧决策，不只是导出代码改动。

## 六、整改优先级汇总（供评审打分）

| 序号 | 偏差 | 优先级 | 类型 | 是否需真实导出复核 |
| --- | --- | --- | --- | --- |
| 1 | 页眉留空 | P0 | 版式 | 是 |
| 2 | 页脚改居中纯数字页码 | P0 | 版式 | 是 |
| 3 | 封面纳入连续页码 | P0 | 版式 | 是 |
| 5 | 正文东亚字体改宋体（防字体替换） | P0 | 稳定性 | 是 |
| 4 | 封面字号校准 | P1 | 版式 | 是 |
| 6 | `（一）（二）` 国网混合编号模板 | P1 | 结构 | 是 |
| — | 技术参数表 / 点对点应答 / 附件体量 | 内容层 | 交付边界 | 与客户确认 |

### 建议执行顺序

1. **P0 版式三项**（页眉留空、页脚纯数字页码、封面连续页码）：肉眼最易发现的不一致，优先整改。
2. **P0 字体项**（正文改宋体）：规避阿里云字体替换，稳定性收益高。
3. **P1**（封面字号校准、国网混合编号模板）：进一步贴近客户稿观感。
4. **内容层**（参数表 / 点对点应答 / 附件体量）：与客户对齐 MVP 交付边界后再决策。

## 七、评审注意事项

1. 所有版式整改建议仅针对 `technical_bid_standard` / `business_bid_standard`（新疆参考分支），**不应影响 `formal_bid_standard` 通用模板**及其他省公司场景。
2. 客户新疆参考稿定位为 `source_domain=tender_requirement` / 中标参考样式，**仅用于抽取版式、目录组织和分册结构**；其企业事实、产品参数、证书、附件内容不得复用到泰昌投标文件。
3. 任一整改实施后，必须走真实导出链路（`build_project_bid_markdown → convert_md_to_word → refresh_docx_fields_with_soffice`）复核，并按规范记录到 `docs/development/runs/` 与本专项 `docs/development/docx-bid-export-quality-todo.md`。
4. 本稿为评审输入，未改动任何导出代码。
