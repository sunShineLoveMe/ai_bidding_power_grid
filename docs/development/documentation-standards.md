# 文档制度

## 目标

文档是项目交付资产的一部分，不是补充说明。团队成员应能通过文档完成环境启动、理解架构边界、定位业务模块、执行常见运维动作，并判断当前方案与历史方案的区别。

## 文档分层

| 目录 | 责任 | 维护时机 |
| --- | --- | --- |
| `docs/deployment/` | 本地启动、部署、环境变量、安全、云资源 | 环境、依赖、部署方式、外部服务变化时 |
| `docs/architecture/` | 架构、数据模型、核心技术路线 | 数据库、存储、模块边界、技术栈变化时 |
| `docs/development/` | 目录结构、API、路线图、开发规范 | 代码结构、接口、团队协作规则变化时 |
| `docs/features/` | 业务功能设计和行为规则 | 产品流程、生成策略、导出规则变化时 |
| `docs/research/` | 调研、方案、客户材料 | 结论沉淀或方案归档时 |

## 必须同步文档的变更

以下变更不能只改代码：

- 新增或修改 `.env.example` 环境变量。
- 修改数据库类型、连接方式、表结构、索引、扩展、迁移脚本。
- 修改文件存储位置，例如 Supabase Storage、本地目录、OSS。
- 修改 Docker Compose、端口、volume、健康检查。
- 修改模型提供商、模型名称、超时时间、重试策略、计费口径。
- 修改上传、解析、生成、导出、在线编辑等主流程。
- 修改部署目标，例如本地、内网服务器、阿里云 ECS/RDS/OSS。

## 写作标准

- 每份文档开头说明用途，避免只堆命令。
- 命令必须可复制执行，路径以项目根目录为基准。
- 环境变量使用 `.env.example` 中的名称，不创造文档专用别名。
- 标明默认值、适用环境和是否敏感。
- 生产环境配置必须写清安全影响。
- 历史方案必须标注“历史/迁移参考”。
- 不把真实密钥、客户文件、账号、公网地址写入文档。

## 变更检查清单

提交前检查：

- [ ] README 或 `docs/README.md` 的入口链接是否需要更新。
- [ ] `docs/deployment/quickstart.md` 是否仍能指导新人启动项目。
- [ ] `.env.example` 与部署文档是否一致。
- [ ] 数据库/存储变更是否更新 `docs/architecture/data-model.md`。
- [ ] 新功能是否有对应 `docs/features/` 说明。
- [ ] 历史 Supabase 内容是否已标注为迁移参考。
