# 《图片型标书功能需求方案》评审意见

评审对象：`docs/development/image-heavy-bid-requirements.md`
评审日期：2026-07-05
评审方式：结合代码库实际核查（非仅凭文档描述），核查范围包括：

- `backend/api/assets.py`（图片资产上传、质量分级）
- `backend/export/md_to_word.py`（DOCX 图片插入实现）
- `backend/api/export.py` / `backend/api/onlyoffice.py`（导出链路）
- `frontend/src/components/editor/TiptapBidEditor.tsx`（编辑器图片插入 UI）
- `docs/development/maturity-assessment-2026-06-07.md`、`docs/development/docx-bid-export-quality-todo.md`

## 一、事实核查结论：文档对现状的描述基本诚实，个别地方有优化空间

这是这份方案最大的优点：它没有夸大现有能力，也没有把"待办"包装成"已有"。具体核实结果：

- **图片质量四级门禁**（`formal_bid_ready`/`knowledge_only`/`review_only`/`restricted`）：真实存在，在 `backend/api/assets.py` 的 `_assess_upload_quality`，且已有基于文件大小、扩展名、文件名关键词（二维码/印章/签名/局部/裁剪）的自动降级规则。文档 8.5 节把它当作"需要新增"的门禁，其实**上传侧已经有雏形**，第一阶段可以直接复用而不是重新设计，方案里没提这一点，算是低估了已有资产。

- **DOCX `withImages=true`**：真实存在且默认开启（`backend/api/export.py`，注释明确写"泰昌 MVP 交付件默认必须图文并茂"）。但实现细节文档没提到两个关键约束：
  - `MARKDOWN_IMAGE_MAX_COUNT` 硬编码上限（`DOCX_MAX_IMAGES` 环境变量，默认 **24 张**），超出直接跳过。这对"图片附件型"（设想是几十上百张证书/报告页）是直接冲突的硬限制，方案第 11.3 节只说"图片过多时需要控制压缩、分页和文件大小"，没有 point 到这个具体代码约束，这会让工程师低估第二阶段的改造量。
  - 图片是逐张顺序插入的普通段落（统一 `5.8in x 8.2in` contain），**没有多图并排、没有整页版式**。这个差距文档 4.2 节其实已经承认了，是自洽的。

- **图片资产 embedding 缺失**：这是文档完全没提到的重大风险。`maturity-assessment-2026-06-07.md` 显示当前 300 个泰昌图片资产 **0 个有 embedding**，向量召回 RPC 因 `embedding is not null` 硬过滤而实际召回为空，现在全靠关键词 fallback。方案 8.2 节设想"支持从知识库推荐相关图片"、8.1 节"支持搜索图片标题、来源文件"，这些功能的可靠性直接依赖语义召回，而底层数据现在是空的。**这是一个应该补进方案风险清单的已知阻塞项**，不补的话，第一阶段做出来的"智能推荐"会名不副实。

- **编辑器图片插入能力**：核实下来比文档描述的还成熟一些——`TiptapBidEditor.tsx` 已支持资产库多选批量插入、分类/关键词检索、本地上传即存资产库。但确实没有文档 8.3 节设想的"正文块/图片块/整页证据块"独立内容块模型，Tiptap 里图片仍是普通 image node，不是结构化的块。这个判断文档写得对。

- **项目级图片包、章节图片排序、导出模式选择**：全库检索零匹配，确认是全新功能，不是"改造现有代码"，方案里也没说是改造，判断一致。

- **预览图**：`output/playwright/image-heavy-ui-preview-20260705/` 下 4 张图确认存在。但没有核实这些是真实产品截图还是设计稿/原型静态图——如果是给客户看的材料，需要在方案里明确标注"UI 预览稿"还是"已实现页面截图"，避免客户误以为功能已经做完。

## 二、方案设计层面的评审

### 做得对的地方

1. **三级强度分层**（图文增强型/图片附件型/混合型）而不是一个简单开关，思路正确。直接做"图片型标书"开关确实会像文档说的那样，无法区分"多插图"和"正文主体全部图片"，混合型的分册级配置才是真实招标场景的常态（技术标要图，商务标承诺函要文字）。

2. **内容块统一底层、导出时按模式排版**的架构原则（第 10.3 节）是对的方向，避免了为三种模式各写一套数据模型。

3. **分阶段路线**（图文增强型 → 图片附件型 → 混合型）风险递增，且每阶段都能单独交付演示，这个节奏务实，符合"MVP 优先解决真实客户试点"的原则。

4. 反复强调"只用泰昌企业事实资产，不混用辽宁/河北豪乾"，与项目 AGENTS.md 里定义的三方 metadata 边界规则是自洽的，没有出现新的边界漏洞。

### 需要补强或存疑的地方

1. **24 张图片上限是硬约束，不是"优化项"**。方案把"控制压缩、分页、文件大小"放在第 12.2 阶段（图片附件型）的隐含前提里，但没有单独列为需要改动的具体代码点。图片附件型如果要塞入几十张证书扫描件，第一步就要改这个常量/逻辑，且要验证 Word 文件在 50-100 张图片时的性能和体积，这应该是第二阶段的第一个技术验证任务，而不是笼统写在风险表里。

2. **embedding 缺失这个已知风险没有被引用**。方案第 8.1 节"支持搜索图片标题、来源文件、报告编号、产品型号"和"支持标记推荐章节"，如果指望语义相似度做推荐，现状是空的。建议在方案里明确：第一阶段的"从知识库推荐相关图片"退化为关键词/分类过滤，语义推荐留到 embedding backfill 完成之后，否则会给客户预期一个实际达不到的效果。

3. **"整页证据页"排版能力被低估了工作量**。这不是简单的"图片块 layout_type=整页"字段问题，而是需要在 `md_to_word.py` 里新增一套完全不同的插入逻辑（页面级布局控制、避免跨页断裂、A4 边距下的整页图适配）。当前 `process_markdown_image` 是基于 Markdown 图片语法逐张处理的，整页证据页可能需要绕过 Markdown 中间层，直接在 docx 生成阶段处理更合适。方案第 11.3 节提到了这个方向但没有展开成具体的技术选型判断，建议在进入第二阶段前先做一次技术预研（spike），确认是继续走 Markdown 中间表示还是新增一条并行的 docx 直出路径。

4. **数据模型的 `sort_order`、`include_in_toc` 等字段设计合理**，但没有说清楚"图片包"和现有 `knowledge_assets` 表、`bid_sections` 表的关系是新建关联表还是往现有表加字段。考虑到 `supabase_repo.py` 已经 2612 行（maturity 文档提到需要拆分），新功能的表设计应该在方案定稿前明确是否复用现有 repo 模块还是新建独立模块，避免继续堆大文件。

5. **验收标准里没有量化的性能/体积指标**。第 13.2 节"文件体积在可接受范围内"这种表述在真实验收时容易起争议，建议在方案定稿阶段就给出具体数字（例如：50 张图片版本的 DOCX 文件体积上限、导出耗时上限），现在改起来成本低，等实现完再倒推指标成本更高。

6. **章节图片排序的"拖拽"功能**——方案自己也说"MVP 可先用列表排序，后续再升级拖拽"，这个降级是对的，但既然编辑器已经有 Tiptap（支持富文本操作），排序 UI 建议直接复用 Ant Design 5 的 `Table` 行拖拽或 `List` 组件，不需要引入额外的拖拽库，方案没写这个约束，容易被执行时过度设计。

---

## 三、总体结论

方案的问题定义、分层设计和路线图是合理、克制的，符合项目一贯的"实事求是"要求，没有发现虚构能力或过度承诺的表述。主要缺口是：

- 遗漏了图片资产 embedding 缺失这个已知的、会直接影响本方案效果的现有风险，应该补进风险表；
- 对 24 张图片硬上限和整页排版的技术复杂度有所低估，建议第二阶段启动前先做一次技术 spike 而不是直接排期；
- 数据模型和现有大文件（`supabase_repo.py`）的整合方式需要在设计阶段明确，避免继续堆大。

建议先补充这三点再定稿，其余部分可以按当前路线推进。如果要往下走，建议先做的是第一阶段（图文增强型）里最小可验证的一步：把现有 `formal_bid_ready` 门禁接入导出前检查，并解决 embedding backfill，这两项风险最低、复用度最高，能在不改数据模型的情况下先给客户看到"图片质量可控"和"图片可被智能检索"的效果。
