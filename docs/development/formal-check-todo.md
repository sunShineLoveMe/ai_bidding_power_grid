# 正式检查模块需求清单与 TODO

更新日期：2026-06-25

适用范围：国家电网单企业正式投标文件检查、导出前门禁、草稿版导出、导出后成品复验。

模块名称：**正式检查**

## 1. 模块定位

正式检查用于在正式投标文件导出前发现硬伤，允许用户导出草稿版，但避免把未达标文件误作为正式投标文件使用。

本模块不替代人工终审，定位为系统级门禁：

- 防漏项；
- 防资料混用；
- 防模型编造；
- 防格式事故；
- 防明显废标风险；
- 防正式 DOCX 成品质量问题。

## 2. 导出策略

| 场景 | 策略 |
| --- | --- |
| 阻断项 = 0 | 允许正式版导出 |
| 阻断项 > 0 | 禁止正式版导出，仅允许草稿版导出 |
| 草稿版导出 | 文件 metadata 和页面提示必须明确标记“草稿版 / 存在未完成正式检查项” |
| 导出后检查失败 | 正式版状态降级为“导出成品检查未通过”，保留问题清单 |

## 3. 状态标记

| 标记 | 含义 |
| --- | --- |
| `[ ]` | 未开始 |
| `[~]` | 进行中或部分完成 |

| `[!]` | 阻塞或需要业务确认 |

## 4. 实施原则

1. 不过度编码，不先上复杂规则后台、工作流引擎或重型数据库设计。
2. 第一版优先采用 JSON 规则文件 + 后端检查服务 + 前端页面。
3. 每条规则必须真实、客观、可解释，不能为了凑数量写空泛检查项。
4. 每完成一项必须同步本文档状态，并写入对应 `docs/development/runs/` 验证记录。
5. 未完成全部功能前，也必须跑真实可执行验证，不能只记录“代码已写”。
6. 正式检查只能给出系统检查结果和风险提示；正式投标仍需人工审核确认。

## 9. 现有散落检查项处理原则

| 现有内容 | 处理方式 |
| --- | --- |
| 条款覆盖率 | 保留，但并入正式检查中的一个子指标 |
| 未响应项 / 高风险未覆盖 | 并入正式检查，不再作为唯一质量判断 |
| 投标确认字段缺口 | 并入正式检查，作为 blocker |
| DOCX 导出 metadata | 并入导出后成品检查 |
| 企业库中文化 / 资料边界检查 | 并入资料边界检查 |
| 页面上重复的“合规覆盖度”表达 | 删除或统一改为“条款覆盖率” |
| 空的、误导性的关联资料按钮或状态 | 删除 |
| 只展示百分比但无处理路径的检查项 | 调整为可跳转、可处理的检查项 |

## 11. 第一批交付验收标准

- 正式检查页面可访问。
- 60 条规则可展示、分类、筛选。
- 至少能自动判断：
  - 客户确认字段缺失；
  - 条款覆盖率风险；
  - 章节正文空缺；
  - 占位符残留；
  - 泰昌 / 辽宁 / 河北豪乾资料边界；
  - 图片资产来源；
  - DOCX 导出后基础成品检查结果。
- 阻断项存在时，页面明确显示“只能导出草稿版”。
- 草稿版导出不冒充正式版。
- 文档记录规则版本、任务优先级和后续 P1/P2。

## 12. 验证与同步要求

每次实现或调整正式检查相关功能后，至少执行以下验证中的相关项：

```bash
PYTHONPATH=. .venv/bin/pytest tests/test_formal_bid_check.py -q
npm run build
```

涉及 RAG、资料边界、企业事实引用时，还必须执行本地 RAG 门禁：

```bash
set -a; source .env; set +a; .venv/bin/python scripts/rag/run_local_rag_gate.py --run-id <run>
```

涉及 DOCX 正式导出时，必须走真实导出链路：

```text
build_project_bid_markdown -> convert_md_to_word -> refresh_docx_fields_with_soffice
```

每次验证完成后同步：

- `docs/development/formal-check-todo.md`
- `docs/development/runs/<run>.md`
- 如涉及 RAG 或资料边界，同时更新 `docs/rag/evaluation-records.md` 和 `docs/rag/todo.md`
